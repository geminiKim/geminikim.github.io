# Repository Instructions

These instructions apply to the entire repository.

## Mandatory article SEO contract

Any task that adds, edits, translates, republishes, or removes a file under `src/content/blog/` must include SEO work in the same change. SEO is part of article completion, not a later cleanup task. Do not deliver an article PR while any requirement below is deferred.

### Before writing

1. Read `PERSONA.MD` and `SOUL.MD` from the local `extracted-content` corpus and use them as the judgment and voice standard.
2. Inspect the content schema, one current English/Korean article pair, `src/data/tag-taxonomy.mjs`, and the verification scripts before editing.
3. Start from the latest `origin/main` in an isolated worktree. Do not modify the protected main checkout.
4. Define the reader's search intent, the article's distinct question, and a working title before drafting. Avoid generic titles that compete only on broad words.

### Source and locale requirements

- Deliver English and Korean files together under `src/content/blog/en/` and `src/content/blog/ko/`.
- Keep `translationKey`, slug, `publishedAt`, `draft`, and ordered tags identical across the pair.
- Localize the visible title, description, body, H1, and accessibility context naturally; do not translate sentence by sentence.
- Give each locale a unique title and meta description. Titles must be at most 80 characters. English descriptions must be 80–180 characters; Korean descriptions must be 40–180 characters.
- Preserve the source-date-only policy: video-derived posts use the source video's date and never add `updatedAt` or retrospective framing.
- For video-derived posts, keep the localized Devpractice source note and name only the actual AI model used; do not name the agent, platform, or wrapper.
- Use current primary sources for claims that can change. Do not invent citations, dates, metrics, quotations, or operational experience.

### Search and internal-discovery requirements

- Use descriptive headings and answer the article's core question in the opening section. Do not keyword-stuff.
- Choose non-empty tags already mapped in `src/data/tag-taxonomy.mjs`. If a raw tag is new, map it in the same change.
- Do not create a new public topic hub unless both locales will have at least two published articles in it; map narrow tags to an existing durable topic instead.
- Add contextual internal links when an existing article genuinely expands a concept. The generated topic and related-article sections are mandatory but do not justify unnatural body links.
- Keep the English/Korean article pair aligned in conclusions, caveats, examples, links, and normative strength.

### Metadata and routing requirements

Canonical URLs, `hreflang`, `x-default`, Open Graph, Twitter cards, `BlogPosting` JSON-LD, RSS entries, sitemap entries, topic links, and related articles are generated by shared layouts and helpers. Do not hardcode duplicate metadata in Markdown or page wrappers. If shared SEO behavior must change, update the shared implementation and its generated-output contract together.

### Required verification before delivery

Run all of the following from a clean production build:

```sh
npm ci
npm run build
node --no-experimental-strip-types scripts/verify-article-seo.mjs
node --no-experimental-strip-types scripts/verify-taxonomy.mjs
git diff --check
```

`npm run build` already runs the complete i18n and SEO suite, including `scripts/verify-article-seo.mjs`. The explicit Node commands prove that the verification scripts do not depend on Node's experimental TypeScript stripping.

Also:

1. Preview the production build and inspect at least one edited English article and its Korean counterpart in a browser.
2. Verify title, description, H1, canonical, language alternates, social metadata, JSON-LD, topic links, related articles, RSS, and sitemap output.
3. Probe changed external links and scan the final diff for secrets.
4. Require the pull-request build check to pass. Do not describe absent or pending checks as successful CI.
5. After deployment, verify the public URLs and generated metadata before reporting completion.

If any check fails, the article is not ready to publish.
